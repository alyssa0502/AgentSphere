# 02 · 平台机制发现

测试过程中顺带摸清的 AgentSphere 平台行为，这些机制是解读读速度数据的前提。

## 1. 热池：每次 create 交付的都是预开机沙箱

- 内核 btime 恒等于 **create 时刻前 20s**（平台流水线常数）——沙箱在 create 之前就已整机预热
- create 交出的沙箱里 envd / UI(3001) / chromium(9222) 全部已在运行
- 顺序、10 并发、30 并发共 60+ 台无一例外；30 并发也打不空池子
- 交付口径：create→UI+浏览器全就绪，顺序 ~0.5-1.3s，30 并发突发 p50 0.86s

含义：**用户侧永远测不到"真实冷启动"**；所有首启动耗时差异实际来自存储层（见下）。

## 2. 冷物化：镜像数据块是懒加载的

- 新镜像建模板后，模板立刻可 spawn（拉起快），但镜像里的**数据块并没有提前落到宿主盘**
- 第一个沙箱首次读纯数据文件时，才触发从中心镜像存储到宿主盘的首次物化：500MB 花 46s（11MB/s）
- 物化是**按需、分层传导**的：首台 46s → 约 30 分钟内传导完成 → 之后的新沙箱首读收敛到 ~2.4s（210MB/s）
- 传导期间存在慢径宿主残留（实测 4%：仍走 71MB/s 慢径）

## 3. 页缓存的三条规则

| 规则 | 实测证据 |
|---|---|
| boot 路径文件永远热 | chromium 二进制 297MB 首读 0.02s——热池预开机时浏览器自读二进制 |
| 跨沙箱无共享页缓存 | 每个新沙箱首读都要重走盘层（~2.4s/500MB），即使是刚被别的沙箱读过的文件 |
| 单沙箱内页缓存留不住 500MB | 同沙箱二读 500MB ≈ 1.0-1.3s（~500MB/s，疑受 VM 内存上限挤压）；小文件（297MB chromium）二读 0.02s |

## 4. 重要修正：一次被推翻的结论

| 时间线 | 现象 | 当时推断 | 后续实验 |
|---|---|---|---|
| 用 chromium 做新镜像+新模板 | 首读仅 1.64s | "平台 build 阶段已预物化" | ❌ 错 |
| 用 500MB 纯数据文件做同构实验 | 首读 46s | — | 真相：boot 路径文件被热池预热读热；纯数据文件无人触碰才暴露真冷层 |

方法论教训：**实验文件的选择会决定你能否看到目标层**——要测存储层，就必须选"无任何进程会读它"的文件。

## 5. UI 慢的 A/B 实验（拉起内部优化）

背景：开机即并行拉 chromium 的模板（2db37b22），UI 就绪要 3-11s。

| 版本 | UI 就绪 | 浏览器就绪 | 结论 |
|---|---|---|---|
| 并行版（开机即拉 chromium） | 3.5s | 3.5s | 两者与系统初始化抢 4 核（cpu.max="max 100000"） |
| watcher 版（等 UI health 再拉） | **1.1s** | 晚 3-5s | UI 干净启动；浏览器作为"第二优先级" |

watcher 启动命令（模板启动命令字段）：

```sh
sh -c 'nohup sh -c "until curl -sf -o /dev/null http://localhost:3001/health; do sleep 0.3; done; chromium --headless=new --no-sandbox --disable-gpu --disable-dev-shm-usage --remote-debugging-address=127.0.0.1 --remote-debugging-port=9222 about:blank" >/tmp/chromium.log 2>&1 & exec /docker-entrypoint.sh'
```

要点：模板控制台的启动命令是**替换式**（不是追加到默认入口），所以必须后台拉 chromium + `exec /docker-entrypoint.sh` 保住原入口。

## 6. 单层镜像的代价

rootfs 快照法打出的镜像只有一个层（详见 [03-镜像制作与推送](03-镜像制作与推送.md)）：

- tag 之间零共享 → 每个新镜像即使 95% 内容相同，平台也当全新数据处理，全量重新物化
- 这是"每个新镜像都要重付一次 L1 冷读"的直接原因
