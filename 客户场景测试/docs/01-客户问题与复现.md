# 01 · 客户问题与复现

## 1. 客户的现象（两轮测试）

**第一轮（11-04 傍晚）——冷读：**

| 项目 | 数据 |
|---|---|
| 读取对象 | chrome 二进制 301MB（Playwright chromium） |
| 第 1 次 | **41.72 秒 ≈ 7 MB/s** |
| 第 2、3 次 | 0.06 秒（页缓存命中） |
| 环境 | 2vCPU / 4GiB / 30GB 盘，镜像与快照全程不变 |

**第二轮（次日 10:19）——隔夜复查：**

| 项目 | 数据 |
|---|---|
| chrome 首读（新沙箱、各自第一次读） | **3.08 秒 ≈ 98 MB/s** |
| libgallium（从未被读过的文件） | 6 秒 |

客户的疑问：第一次为什么那么慢？之后新建的沙箱为什么就快了？"读"和"拉起"是不是一回事？

## 2. 机制澄清：读 ≠ 拉起

- **拉起** = 创建沙箱实例到 UI/浏览器就绪，客户侧实测恒定 ~1 秒（平台热池预开机交付）
- **读** = 沙箱内进程（如 `cat chrome > /dev/null`）把文件完整过一遍 I/O
- 客户的 `cat` 是**纯整文件顺序读**，是读组件的上界；而启动 chromium 进程是 mmap 惰性按需读 + 初始化，两者不是一回事

## 3. 我们的复现（500MB 纯数据文件实验）

设计要点：用 `dd if=/dev/urandom` 写 500MB **纯数据文件**烧进全新镜像（20261105c）→ 建全新模板 → 测首读。纯数据文件没有任何进程会碰它，因此能暴露"从未物化"的真实冷层。

### 阶段一：逐台对照（19:03-19:06）

| 台 | 拉起就绪 | 首读 524MB | 速度 | 端到端 |
|---|---|---|---|---|
| 第 1 台 | 1.17s | **45.97s** | **11 MB/s（真冷）** | 49.2s |
| 第 2 台 | 0.69s | 7.68s | 68 MB/s | 10.9s |
| 第 3 台（补测） | 1.36s | 7.35s | 71 MB/s | 11.1s |

**第 1 台的 46 秒与客户的 41.7 秒几乎完全一致**——冷读层复现成功。

### 阶段二：50 台批量（19:34，测完统一销毁）

| 指标 | 数值 |
|---|---|
| 分布 | 真冷读 **0** 台 · 盘读 50 台 · 页缓存 0 台 |
| 首读 524MB | min 2.13s · **p50 2.54s（210MB/s）** · max 7.41s |
| 端到端 | min 4.56s · **p50 5.11s** · max 10.97s |
| 慢径残留 | 2/50 台（4%）仍为 7.4s @ 71MB/s |

对比 33 分钟前：真冷层已完全消失；稳态读从 71MB/s 提速到 210MB/s。说明物化传导存在一个 **~30 分钟的"慢径→快径"加速过程**，且有少量宿主残留慢径。

### 三层判读口径（500MB 文件）

| 首读耗时 | 层 | 含义 |
|---|---|---|
| > 20s | L1 真冷读 | 数据块从未落到宿主盘，首次物化 |
| 2 - 20s | L2 盘读 | 已物化，新沙箱重走盘层（跨沙箱无共享页缓存） |
| < 2s | L3 快径/页缓存 | 快径传导完成，或文件在开机路径上已被读热 |

## 4. 为什么之前"复现不出"冷读

更早用 chromium 二进制本身做过同构实验（新镜像 + 新模板），首读只有 1.64s——当时推断"平台在模板 build 阶段已预物化"。**该推断被本实验推翻**：真正原因是 chromium 每次开机都会读自己的二进制（开机即拉起浏览器），而平台热池在 create 前 20s 就预开机了沙箱，boot 路径文件因此永远是热的。只有"无进程触碰"的纯数据文件才能测到真冷层。详见 [02-平台机制发现](02-平台机制发现.md)。

## 5. 给客户的口径

- 拉起体验不受影响（恒 ~1s）；首读惩罚只发生在"全新镜像 + 从未被碰过的大文件"组合上，且**每个镜像层只发生一次**
- 首次 40-50s 之后：新沙箱首读 ~7s，约半小时后收敛到 ~2.4s（500MB 量级）
- 若业务在意首读：预热（部署后主动 cat 一遍目标文件）或把大文件放进开机路径
